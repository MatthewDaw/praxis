Grounding Context

Codebase context. agent_factory runs af-build loops over the Praxis knowledge graph: prd-<project>, building-validation, and planning-validation snapshots; category="check" facts own their applies_to predicates and run commands; tickets pin validations at claim via hooks/_ticket_state.py (claim → resolve → pin → verify → finish); seeded_checks.toml is the append-only reusable check library with candidate / promote_universal lanes and a report_only calibration knob. In-flight uncommitted work: wireframe_conformance.py (static parser) and wireframe_browser_check.py (Playwright computed-style/geometry gate, screenshots mandatory, loud failure when the browser is missing).

Where the loop leaks today. Post-merge verdicts live in sentinel files outside the repo and are never recorded on ticket facts; unregistered meta keys silently drop in transit; resolve_finding() had no production caller until commit 4cdc010 (17-round re-dispatch churn); panel findings land undifferentiated with no severity field; auto-skips happen silently; docs/solutions/ is never auto-consulted. Silent driver deaths went unrecorded for 5 and 9 hours.

Why checks got gamed. Seven successive wireframe-conformance attempts all measured a proxy (markup strings, byte volume, dataclass state) instead of an observable property; six tickets shipped unstyled HTML through all nine pinned checks. The retrospective's core finding: “the gap is not strictness, it is sensor capability.” The four failure classes from the sports retrospective — vacuous-truth checks on empty content, acceptance thresholds weaker than coded constraints, reporting presented as gating, unvalidated verifier self-reports — recur across projects.

External research (high value). ImpossibleBench: frontier models exploit visible tests 76% of the time even when told not to; SpecBench: gaming scales +28pp per 10× task size; EvilGenie: measure hacking via held-out tests + LLM judge + verifier-edit detection; Meta's mutation-guided test validation (mutate the artifact, confirm the check fails — 98% agreement with humans); SWE-Bench-Verified hidden-verifier pattern; memory frameworks (Mem0, Zep/Graphiti, Letta, LangMem) standardize episodic/semantic/procedural memory but none convert memory into enforced gates — that conversion is the open gap this project would fill; Obsidian Memory MCP shows markdown-native agent memory with graph links. Cross-domain: ASRS blameless incident taxonomies, WADA lab proficiency testing, hospital M&M conferences, Shepard's legal citators, FAA airworthiness directives.

Institutional learnings. docs/solutions/ has zero prior art on check gaming or failure loops (greenfield). Two adjacent conventions to respect: ticket writes are identity-keyed (never dedup a write-back path); finished_at is server-written.

User-supplied evidence distilled into dossiers: the sports-analysis failure retrospective (44 entries), the build-methodology audit across four projects (11 entries), the wireframe conformance check failures log (15 entries), and the factory failure log (16 entries — arrived mid-run; used in verification), plus five repo evidence dossiers scouted per axis.

Cross-project constraint (added in refinement)

Learnings must live in a shared substrate every project consumes automatically, scaling with project count — not trapped in any one project's space, and not dependent on a single monolithic graph. The survivor set resolves this as a three-tier substrate, two tiers of which already half-exist:

Enforcement tier — git-versioned files, graph-independent
seeded_checks.toml + the defeat-corpus fixtures (idea 3), shipped with agent_factory itself. The promote_universal lane already injects onto every non-exempt ticket in every project from one appended block; fixtures ride alongside. Scales as plain files under PR review; survives graph resets.
Knowledge tier — a shared org-level learnings space in the DEPLOYED Praxis service (hard requirement: cloud-maintained)
User constraint: all knowledge store is maintained in the cloud, in the deployed Praxis service — knowledge living only on a laptop is strictly forbidden. So the canonical store is one org-level shared learnings space (e.g. factory-learnings) in the deployed service, mounted read-only into every project space at claim/resolve time — the existing general-pool mount pattern and copy_snapshot_to_org / org-source primitives are the transport. This resolves the earlier Postgres doubt as a topology fix, not an engine swap: the scaling problem was per-project graph instances; one cloud org-space shared by every project is exactly what the service's org primitives exist for. The docket's disposition promotes a project-local case into a shared-space entry, so the store grows with lessons, not incidents.
Enforcement tier — git-versioned executable gates (code, not knowledge)
seeded_checks.toml + defeat-corpus fixtures stay in the agent_factory repo because they are executable code shipped with the factory — pushed to the remote, pulled by the devbox, never laptop-only. Learned checks blessed at the docket land here (or in the project's building-validation snapshot in the deployed service, per the existing intake paths).
View tier — file projections, always derived, never the home
A markdown export of the shared space (frontmatter per learning, backlinks failure → learning → check → projects protected) gives PR-style review and Obsidian browsing. The 2026 comparative research (idea 6) applies to this layer: markdown+frontmatter is the right projection format; Obsidian is a fine human browser over it but must never be an agent dependency (headless access requires the desktop app). The projection regenerates from the service at any time and is disposable by construction — deleting a laptop loses nothing.

Design consequence: promotion happens at the docket disposition (idea 2) — the same judgment point where a case is deduped against the cross-project taxonomy, so sharing and dedup are one motion.

Intake pattern (added in refinement): learnings come after the fact

No upfront prediction. The canonical cycle is: build → find what went wrong (machine or human) → ingest the learnings → regress the matching tickets → rerun. Speculative pre-authoring of validation content — the af-intake-plan-validation lens pattern, hand-written checks guessing at future failure modes — is explicitly out; it is the authoring style the retrospectives show failing (content authored as engineering upfront; seven predicted wireframe checks defeated in sequence). Every idea in this document operates inside that cycle:

Two failure-finding channels feed ingestion
Machine-found: the existing auto-regression mechanism — when verification regresses a ticket, the system has already concluded “this shipped wrong,” so that event auto-drafts a proposed learning into a quarantined lane of the knowledge store, with the regression_detail evidence attached. Human/Claude-found: post-run review of the ledger (idea 1) surfaces what the machine missed.
Ingestion is the docket
Both channels converge on idea 2's disposition step: bless the drafted learning (corpus entry, optionally with a check), or discard it. Checks are only ever born from real defeats — idea 3's certification pipeline runs at ingestion time on the learned check, with the defeating artifact as its first corpus fixture.
The tail is regress-and-rerun
An ingested gate bulk-regresses matching finished tickets (praxis_regress_requirements — idea 3's recall stage) and the rerun proves the learning actually blocks the failure. A learning that survives ingestion but never re-gates anything is caught by idea 6's uncited-authority report.
Ratified: fully retire speculative check prediction (demote, don't delete)
The speculative authoring workflows — a human or Claude predicting failure modes and hand-iterating checks via af-intake-build-validation or lenses via af-intake-plan-validation — are fully retired as human-facing iteration paths. The commands themselves survive as the docket's write plumbing (their section-locked single-writer role is load-bearing for graph integrity, and the WORK-review panel already emits through them), but the docket becomes their only caller: every check arrives as a learned rule with its defeating artifact as the first certification fixture, and every planning lens is born from a real planning failure dispositioned through the same gate. Accepted cost: a genuinely new domain's first run is unguarded — paid once per failure class across the whole portfolio thanks to the shared org-space, and an urgent gate can still be filed manually as a docket case at any time (same ingestion gate, so hand-added gates get certification and an evidence trail too).

Notifiable failure ledger + failure-class taxonomy (af-retro)

Description
Write category="failure" facts automatically at the chokepoints failure data already flows through: write_build_state regression details, UNVERIFIED downgrades, graded defects[], resolve_finding events, the sentinel-file post-merge verdicts that today die outside the repo, and a heartbeat-miss watchdog so silent driver deaths file their own case. Auto-regression is a first-class emitter: every regression event both files a case and auto-drafts a proposed learning (quarantined until the docket rules on it). Each case is classified into a deduped failure-class taxonomy (vacuous-truth, proxy-metric, self-report-accepted, stale-artifact, dead-wire, silent-key-drop, substring-match-no-backoff…) with derived_from edges to the check that missed it and the ticket that shipped it. The run marker's timestamps bracket the run, so af-retro <project> prints the complete failure list for a run in seconds. New meta keys must be registered loudly — no more silent key drops. Cross-project split: ledger cases stay project-local; the failure-class taxonomy lives in the shared factory-learnings space mounted read-only into every project, so “have we seen this shape before, in any project?” is answerable everywhere.
Basis
direct: “Post-merge verification output (verdict, gates_green, regressed list) lives in SENTINEL FILE outside repo… Verdict is NEVER recorded on ticket facts themselves” and “Unregistered keys silently DROP IN TRANSIT” (failure-capture dossier); 5h/9h silent driver deaths (build-methodology audit). The factory failure log is itself organized as exactly this taxonomy (patterns S1–S3 across F1–F7) — unusually direct corroboration. external: CDC notifiable-disease registries; ASRS incident taxonomy.
Rationale
This is the literal precondition of the ask — you cannot triage what was never written down, and today the richest failure evidence evaporates in /tmp. Because the ledger reads from chokepoints the worker doesn't control, workers cannot suppress their own case files. The taxonomy is what makes learnings transfer across projects: the self-contradictory-verdict bug independently hit two projects before anyone connected them.
Downsides
Failure-class schema needs careful design; class dedup is judgment-heavy (an LLM-assisted step with human override); one more fact category to maintain and migrate.

M&M docket: disposition-forced post-run triage

Description
After each run, compile the ledger's open cases into a docket auto-ranked by measured cost already in the data (rounds burned, tickets touched, checks defeated). The human must disposition every case into exactly one of: → check (af-intake-build-validation, with the check body pre-drafted from the failure's own evidence so approval replaces authoring), → planning lens (af-intake-plan-validation), → ticket, or → accepted-risk (recorded episode, per the existing skip-episode precedent). The docket is the single ingestion gate for both failure-finding channels — auto-drafted learnings from regression events arrive pre-written for bless/discard, human-found failures get authored here — and a disposition that lands a gate closes with regress-and-rerun of the matching tickets. Scope (ratified): the docket becomes the only caller of af-intake-build-validation and af-intake-plan-validation — the speculative human iteration paths through those commands are fully retired. The teeth: the next run's step 0 warns — or refuses, configurable — while undispositioned cases from the last run exist. Panel findings gain a severity field; auto-skip episodes surface in the docket instead of hiding. Each disposition also chooses scope: project-local, or promote to the shared substrate (a universal seeded check, or a lesson in the shared factory-learnings space) — promotion and taxonomy-dedup are the same judgment, made once.
Basis
direct: “Panel emits findings as tickets/checks with no standardized priority/severity field for operator triage. Findings land undifferentiated” and “Auto-skip happens silently with only the episode as evidence” (post-build-review dossier); the resolve_finding dead wire caused 17+ rounds of re-dispatch churn before 4cdc010. external: hospital Morbidity & Mortality conferences — mandatory attendance, severity-selected cases, and a recorded disposition for every case, never silence.
Rationale
All three amend paths already exist and are one call each — what's missing is the forcing function that routes every failure into exactly one of them. This delivers “physically cannot repeat” at the workflow level: a failure observed in run N structurally cannot reach run N+1 without a human having chosen check / lens / ticket / accepted-risk for it.
Downsides
A hard refuse-gate can block urgent runs — needs the warn/refuse toggle; pre-drafted checks still need real review or the library fills with junk gates; docket fatigue if the ledger over-captures (severity ranking is the mitigation).
3learning-to-enforcementConfidence 85%Complexity: High

Check certification lifecycle: born red, kept honest

Description
Checks are only ever born from real defeats — this lifecycle certifies learned checks at ingestion time, never speculative pre-authored ones. Invert the burden of proof: a check is trusted only after it has been shown able to fail. No check gates until it (a) fails the null artifact — an empty/contentless file, a stopped server; (b) fails a mutation of the target toward the exact defect it claims to catch (strip the CSS, remove a control); (c) fails every archived defeat of itself and its ancestors — a permanent defeat corpus of real gaming artifacts, appended whenever a new defeat is discovered in production; and (d) survives a red-team agent whose sole goal is a minimal passing-but-violating artifact. The defeat corpus is git-versioned fixtures shipped with agent_factory — graph-independent and therefore automatically shared: a defeat discovered in any project certifies checks for every project. Later lifecycle stages: fire-rate and pass-margin telemetry (a gate that never fires is a suspect and gets auto-scheduled for re-certification; report_only checks auto-propose promotion after N real catches), and airworthiness-directive recall — a check-version bump enumerates finished tickets whose pass was recorded under the superseded code_hash and bulk-recalls them via praxis_regress_requirements, so hardening a check never silently amnesties past gaming.
Basis
direct: “Six tickets… shipped unstyled HTML through all nine pinned checks” (wireframe dossier); seeded_checks.toml: “TO ADD A CHECK: append one [[check]] block below. That is the ONLY edit needed”; report_only documented as “the calibration-rollout knob”; code_hash already recorded in graded verdicts. external: Meta's mutation-guided test validation (98% human agreement); EvilGenie's verifier-edit detection; ImpossibleBench (76% exploit rate on visible tests); WADA lab proficiency testing — a lab that passes a spiked sample loses accreditation; FAA airworthiness directives.
Rationale
Every one of the seven failed wireframe check attempts would have been rejected at intake by the null probe alone — the cheapest stage of this lifecycle. Five of five ideation agents independently converged on some form of this idea, and it is the only mechanism in the set that catches the next unknown defeat (via corpus + red team + telemetry) rather than the last known one.
Downsides
The most ambitious survivor: red-teaming costs tokens per check; fixture/corpus management is real operational surface; recall can create rework storms and needs batching. Sequencing mitigation: the null probe (one wrapper, no per-check authoring) is a shippable first slice; idea 4 is a strict cheap subset to ship even earlier.

Evidence-sealed verdicts: no pass without proof, no proof without custody

Description
Generalize wireframe_browser_check.py's strongest property library-wide, in two halves. Evidence-mandatory: the default verdict is FAILED; passing requires a non-empty, runner-produced evidence artifact declared per check (evidence: field on every [[check]]); record_validation_pass refuses evidence-less passes; missing tooling is a loud exit-2 failure, never a skip. Custody-sealed: every verdict carries proof the artifact tested is the artifact built — git HEAD of the served tree, process start-time vs last-commit-time, port-owner PID — and a mismatched seal downgrades to UNVERIFIED through the existing b67d5ea coherence-downgrade lane.
Basis
direct: wireframe_browser_check.py:15-21 — “EVIDENCE IS MANDATORY… a run that produced no rendering evidence FAILS, it never passes” (quote verified verbatim by the fresh-context verifier); “Stale processes (13-minute-old server), wrong routes, and stale port bindings produce passes indistinguishable from real passes” (wireframe dossier); b67d5ea confirmed in git log. external: doping-control chain-of-custody — a broken seal voids the result regardless of the assay.
Rationale
The strongest anti-gaming property in the codebase currently exists in exactly one file. Vacuous passes, empty-diff auto-passes, silent skips, and stale-process false results are all instances of “pass without sealed evidence” — one structural rule kills the whole class, and the reference implementation already exists. Cheapest high-confidence win in the set; ship first.
Downsides
Every existing check needs an evidence declaration (a migration pass); trivial-evidence checks (pure lint) need a sensible floor so the rule doesn't become ceremony.
5check-hardeningConfidence 85%Complexity: Low

Sensor-capability floor at check intake

Description
Every check declares its instrument class (filesystem-grep / static-parse / exit-code / browser-computed / LLM-judge / human) and the observable property it claims to gate. af-intake-build-validation carries a small lookup table mapping property categories to the minimum instrument class — visual conformance requires browser-computed or higher; content soundness requires human — and mechanically rejects mismatches, so a text-grep claiming to prove visual layout is unauthorable. Corollary: prefer checks compiled from reference artifacts (a parsed wireframe, a recorded trace) over hand-written prose assertions — the one check family that caught real defects (attempt 7) is the one derived from rendering the reference.
Basis
direct: “Assert through an instrument that can observe the property… the gap is not strictness, it is sensor capability” (wireframe dossier, quoted verbatim — the verifier rated this the best-grounded candidate in the set); the check-hardening dossier's gameable-spots table is six instances of instrument/property mismatch; “Wireframe spec is DERIVED from source — never hand-written”. external: Goal Structuring Notation safety cases — evidence must carry an explicit argument linking it to the claim.
Rationale
Attacks the root cause of all seven failed check attempts rather than any one symptom. It converts the hardest-won retrospective insight into a structural authoring gate: check attempt 8 with a grep claiming a styling property cannot exist, rather than being caught six tickets later.
Downsides
The classification table needs occasional maintenance as new property categories appear; borderline properties (content quality) still resolve to LLM-judge/human classes, which carry their own calibration weaknesses — this floors the sensor, it doesn't perfect it.
6learning-storageConfidence 70%Complexity: Medium

Shepardized learnings: no learning without a citing gate (cloud Praxis store, file projections)

Description
Borrow the legal citator: a precedent nobody cites is presumptively dead. Every learning — Praxis insight, docs/solutions/ file, ledger case — must carry an enforcement pointer (the check_id or lens that operationalizes it) or an explicit enforcement: none because <reason> waiver. A standing “uncited authority” report lists learnings no gate cites — that list is the triage queue. docs/solutions/ frontmatter applies_when compiles into an applies_to predicate so learnings enter the same resolve query as checks. The canonical store is a shared org-level learnings space in the deployed cloud Praxis service (hard user constraint: knowledge must be cloud-maintained, never laptop-only), mounted read-only into every project space so recall is automatic everywhere. Backlinks run failure → learning → check → projects protected; the project ledger (idea 1) feeds it via docket promotion, and enforcement predicates resolve from the shared space in the same query lane as checks. File projections are derived, never the home: a regenerable markdown export (frontmatter per learning) provides PR-style review and Obsidian browsing, and the service's contradiction/supersession machinery — the thing markdown memory structurally lacks (Zep's critique) — stays authoritative. Knowledge-layer selection (2026 comparative research, 11 candidates — re-scoped to the projection layer and the steelman by the cloud constraint): the accepted path is the research's “shared Postgres” steelman — one org-level space in the deployed service, per-project isolation via org/space primitives — with its known gap (no native data diff/PR review) closed by the markdown projection + human-gated docket writes. Obsidian — human browser over the projection only; disqualified as an agent path headless (MCP servers require the desktop app; Dataview has no headless engine). Dolt — the runner-up if data-native diff/branch/review ever needs to be first-class in the store itself (used by Beads for coding-agent memory). Graphiti/Zep — best off-the-shelf temporal semantics; a benchmark for what the shared space's supersession model should do, not a replacement for the deployed service. Rejected: KuzuDB (archived Oct 2025), Logseq (format frozen / DB unstable), Mem0 self-hosted (3-container stack), Letta (agent runtime, wrong shape), Oxigraph/DuckPGQ (build-the-access-layer-yourself; research-stage), laptop-local markdown as canonical store (violates the cloud constraint by construction).
Basis
direct: “write a flat doc to docs/solutions/, which nothing retrieves automatically” (learning-storage dossier); the sports retrospective's sharpest entry — a lesson documented as stinging on R26, then repeated on R37: a written lesson with no citing gate protected nothing. external: Shepard's Citations; Obsidian Memory MCP (markdown-native agent memory with graph links). A generation-time postmortem statistic (0% ex-ante / 87% ex-post) did not survive verification and is excluded as unsourced; the mechanism doesn't depend on it.
Rationale
The storage problem isn't location — three storage surfaces already exist — it's that storage and enforcement are disconnected graphs. Making the citation edge mandatory turns “did we actually learn this?” into a queryable property, and it answers the Obsidian question the right way round: a view you'd enjoy browsing, backed by the graph that actually enforces.
Downsides
Mandatory pointers add authoring friction to every learning write; the waiver escape hatch degrades into a rubber stamp unless the uncited-authority report is actually reviewed (pairs naturally with idea 2's docket). The promotion step (project ledger case → shared-space entry) must be reliable — a dead wire there recreates the resolve_finding failure one level up; and the markdown projection must stay strictly derived (regenerable, never hand-edited as the source), or two sources of truth drift.

Protected verification pipeline

Description
Extend the existing invariant “the ticket agent cannot touch check definitions” to everything that grades work. Hash seeded_checks.toml, the conformance scripts, and the gating logic at claim time; any out-of-band diff (outside an af-intake-* write path) is itself a blocking universal failure. Give the driver/verifier code its own regression suite that must be green before any run starts — because harness bugs produced false passes just as surely as agent gaming did: the force-land NameError silently ate a regression call, verdict=pass + gates_green=False counted as pass for 16 hours, and || true wrappers forged quiet passes (the factory failure log's “silent twins of loud bugs” pattern). Formalizing the read-asymmetry (builder sees the criterion; the executable assertion set stays out of the ticket context) folds in here as a documentation-and-mount concern rather than a new capability.
Basis
direct: build-methodology audit P0-3 (NameError crash — 27 min + 9 h silent downtime across two projects) and P1-5 (incoherent verdict passed); commits b67d5ea / b9a90f4 confirmed in git log; factory failure log S2 pattern (“loud version crashes, quiet version forges passes via || true wrappers”). external: the reward-hacking mechanics taxonomy — editing the verifier is the highest-value attack, so the verifier is the asset to protect.
Rationale
Every other idea in this set assumes the verification pipeline is trustworthy; this is what keeps that assumption true as the check library grows into an asset worth attacking. The evidence shows “un-gameable” is undermined equally by agent gaming and by harness bugs — both classes need gates.
Downsides
Integrity hashing adds friction to legitimate check edits (must flow through intake); the harness regression suite is a standing maintenance cost; false-positive integrity trips during development need a sanctioned override path.
